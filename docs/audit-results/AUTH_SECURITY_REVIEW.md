## Summary

Confirmed findings by severity: Critical 0 / High 0 / Medium 0 / Low 1.

Registration exposes whether an email already belongs to an account. No account takeover, cross-account profile access, password/token disclosure, or reset-token replay vulnerability was confirmed in the reviewed scope. This is a static assessment, not a production security certification.

## Findings

### AUTH-001 — [Low] Public registration discloses account membership

- Evidence: src/app/api/auth/register/route.ts:22–45 accepts unauthenticated input, validates it, consumes registration limits, and queries the supplied email. Lines 44–45 return HTTP 409 with `An account with this email already exists.` Lines 16–17 return the same disclosure for a concurrent unique-constraint collision. A previously unused email instead proceeds to creation and HTTP 201 at lines 47–59. src/lib/auth-validation.ts:9 and src/lib/email.ts:2–3 normalize the candidate. script/auth-security.test.ts:88–115 explicitly expects the existing OAuth email to return 409; this test was read, not run.
- Attack path: An unauthenticated attacker submits a valid registration body containing a candidate email and an arbitrary compliant name/password/confirmation. Within available rate-limit budgets, 409 identifies an existing account, including OAuth-only accounts. Neither an authenticated session nor mailbox access is required. A nonexistent address is registered, so comparisons must use controlled addresses during verification.
- Impact: Disclosure of DevStash membership for a known email, useful for targeted phishing or credential attacks. Severity is Low because the response exposes only membership, gives no access to account content, and shared network/per-email limits constrain collection. Throttling does not conceal the first membership answer.
- Verification: Confirmed by complete handler/validation/limiter/schema trace, not a live request or timing inference. In a disposable environment, submit one valid body for an existing controlled email and one for a new controlled email; compare status and body. The existing branch returns 409 before hashing or delivery, while successful creation returns 201. The generic forgot-password response at src/app/api/auth/password-reset/route.ts:24–36 does not prevent this alternate oracle.
- Specific fix: Redesign POST registration and its client contract to avoid an externally observable existing-versus-new outcome: use the same generic status/body for existing emails and accepted registrations, including P2002 collisions. Update src/components/auth/RegisterForm.tsx:34–63 so automatic sign-in success/failure does not reintroduce a public account-existence distinction; consider completing registration through mailbox confirmation if membership privacy is required. Do not disclose whether delivery or creation occurred. Merely changing the error sentence leaves the status/success oracle intact.
- Regression verification: With controlled existing credentials, existing OAuth-only, and new addresses, assert indistinguishable public registration status/body, including case/whitespace variants and concurrent duplicate submissions. Verify no private user fields are returned and inspect the resulting browser flow for a secondary membership oracle. Keep duplicate prevention and throttling tests.
- Sources: Application code establishes this finding; no uncertain external behavior is needed.

## Passed Checks

These controls were confirmed in source; none denotes a runtime test pass.

- **Server validation and password handling:** Shared schemas validate normalized email, minimum password length, matching confirmation, and the actual UTF-8 72-byte bcrypt limit (src/lib/auth-validation.ts:4–29). Registration/reset/profile changes hash with bcrypt cost 12 (register/route.ts:47, password-reset.ts:47, profile-account.ts:32); credentials compare the hash and return only identity fields (src/auth.ts:29–46). Explicit registration fields prevent plan/hash/verification mass assignment (register/route.ts:41–50). bcryptjs 3.0.3's installed index.js:317–325 confirms the byte-limit behavior.
- **Persistent throttling:** src/lib/auth-rate-limit.ts:26–55 performs a parameterized atomic PostgreSQL upsert, uses database time, saturates counters, HMACs keys with AUTH_SECRET, and throws on storage failure. Lines 58–73 enforce network and normalized account budgets; src/auth.ts:24–37 runs both inside authorize, covering direct credentials callbacks. Registration lines 24/42 and password-reset route lines 12/24 invoke their budgets before lookup/hash; reset submissions consume the network budget. Verification resend is per-session-user limited (verification/route.ts:43–59); profile password/deletion attempts are per-user limited before comparison (profile-account.ts:27,48). No trusted header is used unless configured; malformed/multiple-IP values fall back to the shared key (auth-rate-limit.ts:59–65). Actual proxy trust remains unverified.
- **Canonical identity and safe OAuth defaults:** src/lib/auth-adapter.ts:8–23 normalizes OAuth create/lookup/update without replacing account linking; credentials and registration use the same normalizer. prisma/schema.prisma:34 and migrations/20261026234550_auth_identity_and_throttling/migration.sql:4–20 enforce canonical uniqueness and abort migration collisions. No dangerous email-linking override is set. Installed @auth/core 0.41.3 lib/actions/callback/handle-login.js:213–250 requires an authenticated linking context or rejects a new OAuth identity matching an existing email. Migration application was not checked.
- **Purpose-bound bearer tokens:** email-verification.ts:7–8,26–32 and password-reset.ts:17–24 generate 32 random bytes, persist SHA-256 digests, namespace purpose/user/email, and set 24-hour/30-minute expiry. Consumers validate syntax, purpose, current email, and expiry (email-verification.ts:53–66; password-reset.ts:35–59). OAuth-only users cannot gain passwords through reset (password-reset.ts:45–46; password-reset/route.ts:28–32).
- **Single-use transactions:** Verification conditionally deletes the unexpired token before updating the matching account and removing siblings inside one transaction (email-verification.ts:55–66). Reset conditionally updates the prior password hash, conditionally consumes the unexpired token, throws to roll back a failed consumption, and removes sibling tokens (password-reset.ts:49–64). The conditional hash update serializes simultaneous resets using different links. PostgreSQL's documented update-condition recheck supports this reasoning under Read Committed; the database engine version/isolation were not queried. See [PostgreSQL transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED).
- **Recovery responses and token exposure:** Password-reset requests defer account lookup/delivery until after the generic response (password-reset/route.ts:24–36). Unknown/passwordless users share that response; delivery errors log a fixed message. Both email senders build links exclusively from configured APP_URL/AUTH_URL, enforce HTTPS except local development, and bound provider calls to ten seconds (password-reset.ts:9–32; email-verification.ts:13–48). Logs contain configuration booleans/provider status/code rather than bearer links. Token pages specify no-referrer/no-index metadata (reset-password/page.tsx:5; verify-email/page.tsx:5). No third-party analytics request or explicit raw-token logging was found in the reviewed root/auth components; infrastructure URL logging was not inspected.
- **Mutation authorization and ownership:** Every exported profile Server Action obtains the server session and derives the user ID from it (src/actions/profile.ts:6–15). Password change verifies a stored password, rejects passwordless accounts, conditionally updates the previous hash, and invalidates reset links transactionally (profile-account.ts:23–38). Deletion validates exact DELETE, checks the password when present, and transactionally deletes tokens/user with a matching current hash (lines 44–58). Client-supplied owner/plan fields are never used. Passwordless deletion relies on the authenticated session as the implemented policy; no fresh OAuth challenge is claimed.
- **Deleted-user and serialization boundaries:** getCurrentUser obtains a session and checks that its user still exists, selecting only safe fields (src/lib/current-user.ts:8–21). Profile reads and counts use that identity; only a hasPassword boolean crosses to ProfileActions, not the hash (profile/page.tsx:13–20,40). Dashboard queries derive IDs from the same guard (dashboard/page.tsx:17–23; DashboardSidebar.tsx:42–46), and collection joins check both owners (db/collections.ts:39–46). Auth.js session callbacks expose token.sub rather than client-controlled IDs (src/auth.ts:52–56). No persistent cross-user application cache was found in these flows.
- **Deletion artifacts and request protections:** profile-account.ts:52–57 removes current namespaced tokens; initial migration lines 205–238 declares auth/content cascades. Missing/deleted users cannot mutate through profile helpers. Verification and reset custom POST routes explicitly reject differing Origin headers (verification/route.ts:12–16; password-reset/route.ts:9–10). Profile mutations use Next.js Server Actions, whose same-origin POST protections are documented in the installed 16.4.2 data-security guide and [official guide](https://nextjs.org/docs/app/guides/data-security#allowed-origins-advanced). Authorization is present independently of those protections.
- **Redirect/session policy:** SignInForm.tsx:26–32 constrains client callback paths; no application redirect callback overrides Auth.js's same-origin default (installed @auth/core/lib/init.js:13–19). JWT strategy is explicit (src/auth.ts:50); installed core init.js:38,72–84 defaults to a 30-day idle lifetime and actions/session.js:38–47 renews expiry when issuing a refreshed token. Password resets/changes do not revoke existing JWTs, so this is not an absolute 30-day cap. Deleted-user database guards still deny protected data/actions. A forged session-claim update path was not found.

## Review Limitations

- Static review only. No tests, lint, type check, build, browser session, concurrent live request, database query, or real email was executed. Existing regression assertions are evidence of intended coverage, not current passing results. In particular, service-level profile tests do not establish end-to-end Server Action authorization behavior.
- Environment secret values were not read. Production AUTH_SECRET strength/consistency, APP_URL/AUTH_URL, verification toggle, provider configuration, reverse-proxy header overwrite/origin isolation, TLS/cookies, deployed migrations, PostgreSQL version/isolation, and provider delivery remain unverified. Configuration-dependent concerns are not findings.
- The deployment's after/waitUntil support and time budget were not inspected. The installed Next.js after guide states post-response execution depends on platform support and maximum duration; insufficient support could prevent recovery delivery. No deployed failure was demonstrated.
- Existing sessions remain usable after password change/reset by documented policy. A party already holding a valid JWT can continue using it, potentially renewing it through session responses; no revocation boundary is implemented. This behavior is recorded as a policy/threat-model limitation rather than automatically classified as an Auth.js or application vulnerability.
- GitHub callback behavior was traced through installed framework source, not interactive provider login. Framework-managed internals were not exhaustively audited, and no dependency advisory scan was performed.
- Verification-token submission has no dedicated request limiter; its 256-bit bearer secret prevents a demonstrated guessing attack in this review. No measured resource-exhaustion exploit was established, so no severity is assigned. Infrastructure access logs, observability exports, email scanners, and third-party deployment instrumentation could not be inspected for token URLs.
- Physical R2 deletion is a documented future upload-lifecycle responsibility; current implemented authentication/account deletion was reviewed at database level. Maintenance/seed scripts are not public authentication entry points and were not executed.
